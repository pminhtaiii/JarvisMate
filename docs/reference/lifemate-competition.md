# LifeMate: Voice-Driven AI Agent Competition

## Overview

Voice is becoming the main way people talk to machines. The next generation of devices—smart speakers, in-car assistants, smart TVs, earbuds, watches, home robots—will have small screens or none at all, yet they will connect to the same apps and services people already rely on.

* A parent tells the living-room speaker to cool the house before leaving the office.
* A driver asks the car to pay the electricity bill.
* An office worker tells their earbuds to book a ride home after a late meeting.
* A shop owner asks the kitchen speaker to order lunch for the staff.
* A grandparent who never learned to use apps asks the TV to set a reminder to take medicine.

On a phone, each of these tasks takes many taps across several apps; on a screenless device, it is only possible if the assistant can act on its own—yet today’s voice assistants mostly answer questions rather than act. What people want is to simply say it in plain Vietnamese—*“Tôi sắp về nhà, bật điều hòa phòng khách và đặt xe đón tôi”*, *“Chuyển cho mẹ 500 nghìn”*, *“Tắt hết đèn tầng một”*, *“Nhắc tôi họp lúc ba giờ chiều mai”*—and have it done.

**LifeMate** challenges you to build an AI agent that turns spoken Vietnamese requests into actions: given an audio request, the user’s context, and the apps and services connected to the device, the agent plans the steps, calls the right tools with the right arguments, and leaves every app in the state the user asked for—or asks for the missing information when the request is incomplete, and takes no action when no installed app can handle it.

The agent is judged on **what it does, not what it says**. The competition data is anchored in everyday Vietnamese digital life (smart home, banking, ride-hailing, food delivery, email) with requests spoken in synthetic and real voices from the North, Central, and South regions, but the capability you build is general: voice-driven, multi-step tool use by an AI agent that can run on any device, from phones to smart speakers to cars.

## Task Specification

### Input
* **A spoken request:** An audio file with the user’s latest request in Vietnamese, possibly mixed with common English words.
* **User context:** Current time, timezone, location, and a user profile (e.g., home and work addresses).
* **Available apps:** The apps connected to the device (smart home, banking, ride-hailing, food delivery, email, etc.), each exposing a set of tools described by a JSON schema.
* **Conversation history:** Earlier turns of the same conversation, if any.
* **Simulated environment:** Holding the user’s app data (devices, accounts, reminders, contacts, etc.), which the agent can read and change **only** through tool calls.

### Output
The agent produces an ordered list of tool calls (tool name and arguments) to handle the user's request. Depending on the request and the information available, the agent may:
* **Execute actions:** Call the necessary tools in sequence to complete the task and achieve the expected final app state.
* **Request missing information:** Call `sys.ask_missing_info` to specify the intended tool and missing parameters when additional information is needed. This may happen after other tool calls have already been executed.
* **Handle out-of-scope requests:** Return an empty list of tool calls (`[]`) if none of the available apps can handle the request.
* **Final state hash:** Along with the tool calls, the agent submits a `state_hash` generated by the execution environment (`env.get_state_hash()`), which is used to verify the final app state.

### Example
* **Input:**
  * **Audio:** *“Tôi sắp về nhà, bật điều hòa phòng khách 26 độ và đặt xe đón tôi.”*
  * **Context:** The user is at work (`227 Nguyễn Văn Cừ, Quận 5, TP.HCM`), and `user_profile.home` is `123 Trần Hưng Đạo, Quận 5, TP.HCM`.
  * **Installed apps:** `smart_home`, `ride`, `banking`, `email`.
* **Output:** The agent first reads the device list to find the living-room AC, then sets it and books the ride. The submission line for this sample (one JSON object per line in `submission.jsonl`) is:

```json
{
  "id": "s_000123",
  "tool_calls": [
    {"name": "smart_home.get_status", "arguments": {}},
    {"name": "smart_home.climate_set", "arguments": {"device_id": "ac_living_room", "mode": "cool", "temperature": 26}},
    {"name": "ride.book", "arguments": {"from": "227 Nguyễn Văn Cừ, Quận 5, TP.HCM", "to": "123 Trần Hưng Đạo, Quận 5, TP.HCM"}}
  ],
  "state_hash": "9f2c4e7a1b8d3f60"
}
```

## Evaluation Metrics

Each sample is scored on two things: whether the agent leaves the app data in the correct final state, and how closely its tool calls match the reference (gold) calls.

* **State match:** The submitted `state_hash` must equal the gold `state_hash`, otherwise the sample scores `0`. Free-text (fuzzy) fields do not affect the hash. The `state_hash` must be computed by the `zaic_tools` environment (`env.get_state_hash()`) and can be reproduced by the organisers, who replay the submitted `tool_calls` in order with the matching version of `zaic_tools`; if the results differ, the organisers' result is final.
* **Tool-call match:** A submitted call matches a gold call when the tool name is the same, every non-fuzzy argument is identical, and every fuzzy argument has `token-F1 > 0.6` (after lowercasing and Unicode NFC). Each call can match at most one call; order is not considered.
* **Out-of-scope samples:** If the gold list is empty, the sample scores `1` only when the submitted list is also empty.
* **Missing information:** `sys.ask_missing_info` is scored like any other tool.

### Scoring Formula
* **If the gold list is empty:** The sample scores `1` only when the submitted list is also empty; otherwise it scores `0`.
* **Otherwise (the gold list is not empty):**
  * $P$ = Precision: $\frac{M}{M + U}$
  * $R$ = Recall: $\frac{M}{\vert{}G\vert{}}$
  * $F_1 = \frac{2PR}{P + R}$ (gated by state match: $0$ if `state_hash` does not match gold `state_hash`)
  * **Variables:**
    * $M$: Number of matched calls
    * $\vert{}G\vert{}$: Number of gold calls
    * $U$: Number of unmatched submitted calls (including calls rejected with a schema error)
    * $N$: Number of samples in the test set

## Dataset & Directory Structure

The data has three splits with the same layout:
* `train`: ~1,600 samples with labels
* `public_test`: ~600 samples, for the public leaderboard
* `private_test`: ~600 samples, released after the final Docker solution is frozen

### Folder Structure
```text
<split>/                                  # train | public_test | private_test
├── audio/<id>/<id>.wav                   # spoken request of each sample
├── <split>.jsonl                         # one sample per line
├── <split>_tools_catalog.json            # schema of every app tool
├── <split>_environment/<id>/state.json   # initial app data of each sample
├── sample_submission.jsonl               # public_test only
└── zaic_tools/                           # execution environment library for this split
```

### Files Description
1. **Audio (`audio/<id>/<id>.wav`):** The user’s latest request and every earlier user turn in history, in Vietnamese with some common English words (e.g., "book", "AC"). WAV, 16 kHz, mono, 16-bit; ~100% recorded by real speakers of different ages, genders, and regions (North, Central, South).
2. **`<split>.jsonl`:** The input of each sample—`id`, `audio` path, user `context` (`current_time`, `timezone`, current location, `user_profile`, `installed_apps`), and earlier conversation turns (`history`). Train samples also include `audio_text` (the transcript of every user turn) and the `label`: the gold `tool_calls`, their `tool_results`, and the `final_state` (the full data of every app the gold calls changed).
3. **`<split>_tools_catalog.json`:** The apps of the split and the schema of every tool—`name` (`app.tool`), `description`, `kind` (`read`, `write`, or `meta` for `sys.ask_missing_info`), `parameters` as JSON Schema, and a short summary of the returned fields.
   * Parameters may carry `x-ref` (must be a valid ID in the app data), `x-match: "fuzzy"` (free text, scored by token-F1), and `x-one-of` (at least one of the listed groups is required, e.g., `contact_id` or `phone_number`).
   * The catalog covers the whole split; the tools a sample may call are those of its `context.installed_apps`.
4. **`state.json`:** The initial app data of a sample (devices, accounts, contacts, reminders, etc.), with the actions of history already applied, plus a `_meta` block (`question_id`, `current_time`, `tools`). **It is loaded by the environment; the agent must not read it directly.**

## Execution Environment (`zaic_tools`)

The organisers provide the `zaic_tools` Python library, which simulates the apps locally. Each sample runs in its own `ToolEnv`, which must be created only once. The environment checks each call against the tool schema, executes it, updates the app data, and returns the result, which the agent can use in its next step.

A call fails with `"ok": false` and an error message, typically when the tool does not exist or an argument has the wrong data type. Only tools from the apps listed in `context.installed_apps` (plus `sys.ask_missing_info`) may be called. Every call, successful or not, is logged; this call log, together with the final state hash, forms the submission. Each split comes with its own version of `zaic_tools`.

```python
import sys
sys.path.insert(0, "public_test")              # zaic_tools of the split
from zaic_tools import ToolEnv

# Create one environment per sample; root is the folder that holds the split folders
env = ToolEnv("public_test", "public_0001", root=".")

# Check arguments against the tool schema (nothing is executed)
env.validate("smart_home.light_set", {"power": "off"})
# -> {"ok": false, "error": "thiếu tham số bắt buộc: device_id"}

# Execute a call
# -> {"ok": true, ...} or {"ok": false, "error": "..."}
env.call("smart_home.get_status", {})

# Call log and final state hash for submission
env.get_tool_calls(), env.get_state_hash()
```

> **CRITICAL RULE:** The agent/solution must **not** read, copy, or parse any file under `<split>_environment/` (including `state.json`); all app data is accessed only through the organisers' `zaic_tools`, with exactly one `ToolEnv` per sample, and every call made on it must appear in the submission.

## Inference & Submission

### Inference Template
The template below runs the agent on every sample of a split and writes `submission.jsonl`: one line per sample with `id`, `tool_calls`, and `state_hash`. Run it from the folder that holds `public_test/`. Create exactly one `ToolEnv` per sample inside `infer()`.

```python
import json
import sys
from pathlib import Path

ROOT = Path(".")                                  # folder that holds public_test/
SPLIT = "public_test"
sys.path.insert(0, str(ROOT / SPLIT))             # zaic_tools of the split
from zaic_tools import ToolEnv

def infer(item):
    env = ToolEnv(SPLIT, item["id"], root=ROOT)   # one environment per sample
    # Your pipeline: ASR (ROOT / SPLIT / item["audio"]) -> LLM -> env.call(tool, arguments) -> LLM -> ...
    # e.g. env.call("smart_home.get_status", {})
    #      env.call("smart_home.light_set", {"device_id": "light_kitchen", "power": "off"})
    return env.get_tool_calls(), env.get_state_hash()

with open(ROOT / SPLIT / f"{SPLIT}.jsonl", encoding="utf-8") as fin, \
     open("submission.jsonl", "w", encoding="utf-8") as fout:
    for line in fin:
        item = json.loads(line)
        tool_calls, state_hash = infer(item)
        fout.write(json.dumps({
            "id": item["id"],
            "tool_calls": tool_calls,
            "state_hash": state_hash
        }, ensure_ascii=False) + "\n")
```

### Submission File Format
The file must be UTF-8 JSON Lines (`.jsonl`) with exactly one line per sample in the split; see `sample_submission.jsonl` for the format.

**Example (`public_test/sample_submission.jsonl`):**
```jsonl
{"id": "public_0039", "tool_calls": [{"name": "alarm.list", "arguments": {}}, {"name": "alarm.create", "arguments": {"time": "2026-11-11T05:30:00+07:00"}}], "state_hash": "461fcd40…"}
{"id": "public_0001", "tool_calls": [{"name": "sys.ask_missing_info", "arguments": {"tool_name": "music.add_to_playlist", "params": ["playlist_id", "track_id"]}}], "state_hash": "c83200c2…"}
{"id": "public_0002", "tool_calls": [], "state_hash": "0c9a2ec0…"}
```

## Competition Rounds

The competition runs on a leaderboard with two rounds:

1. **Round 1 — Public Test:** Teams develop their solutions, run them on `public_test`, and submit the results. Scores appear on the public leaderboard and are for reference only during development.
2. **Final Solution Submission:** The final solution is submitted as a Docker image, following the organisers’ separate guidelines. For scoring, the organisers mount the private test folder (same structure as `public_test`) into the container at `/data`, run the inference script, and collect the result at `result/submission.jsonl`. The container must run fully offline, with no network access.
3. **Round 2 — Private Test:** After teams submit and freeze their solutions, the organisers release `private_test` and its environment. Teams run their frozen solution with the provided `zaic_tools` and submit the results. The organisers re-run the submitted Docker image to verify the results, and the final ranking is based on the `private_test` score.

## Technical Requirements & Rules

Every solution must meet all of the following requirements:

* **Model Size:** The whole system (ASR, LLM, and any other components) must have **fewer than 6B parameters in total**. The LLM must have **fewer than 5B parameters** and a context length of **at most 16K (16,384) tokens**.
* **Data Access:** The agent must **not** read, copy, or parse any file under `<split>_environment/` (including `state.json`) directly; all reads and writes must go through the `zaic_tools` execution environment, with exactly one `ToolEnv` per sample, and every call made on it must appear in the submission.
* **Allowed Data and Resources:** Teams may use public data and open-source models released **before 26 October 2026**, provided their licences allow it. Synthetic data may be generated with other services or models (LLM, TTS, etc.) during development, but these must not be used at inference. Labelling `public_test` or `private_test` (manually or with external services or models) to train or tune a solution is strictly prohibited.
* **Runtime and Hardware:**
  * Each sample must be processed within **30 seconds**; samples that time out or fail to execute score `0`.
  * The solution must run **fully offline**, with no external APIs or services at inference.
  * **Scoring Hardware:** 1x NVIDIA A30 GPU, 16-core Intel Xeon Gold 6442Y CPU, and 64 GB RAM.
* **Reproducibility:** Fix all random seeds (Python, NumPy, PyTorch, etc.) and use deterministic decoding for ASR and LLM (such as greedy decoding or `temperature = 0`). If a re-run differs from the submitted results, the organisers run the Docker image 5 times and use the average score as the official score.
* **Tie-Breaking:** If teams have the same final score, the organisers re-score their `tool_calls` with the F1 formula, ignoring the `state_hash` check. If they are still tied, the team with the lower average processing time per sample ranks higher.
